▸ The territory this sits in: data architecture, as seen from here

The frame. Data architecture exists so that a number can be asked for by someone who did not produce it, and still be trusted, affordable and explainable afterwards. Everything in the field is one of four pieces of furniture around a store: a dictionary (what the number means and who owns it), a gate (who may ask, in what shape), a log (what actually ran) and a test (does the number still mean what the dictionary says). This playground is that sentence with a model as the asker instead of a dashboard.

RoomWhat it is
Storage shapesWhere rows live: a warehouse (Snowflake, DuckDB), a lake or lakehouse (Databricks); row stores versus column stores.
ModelingFacts (events with amounts) and dimensions (the things events are about), and the grain: what one row stands for.
PipelinesHow rows arrive and are transformed into the model, on a schedule, with tests between steps.
Semantic layerThe dictionary: each business number by name, with definition, owner, version and query.
Access and policyWho may read which rows and columns, written down and enforced at the store or the gate.
ObservabilityLineage (where a number came from), traces (what ran), cost per query, drift watches.
Quality and testingTests on the data (freshness, uniqueness, ranges) and on the answers (evals against an independent key).
The agent as clientA model asking the store through tools: MCP, skills, estimate before execute.

▸ Questions you don't know to ask yet

Primitives: what is a grain, really, and why does every bug here (double attribution, late payments, duplicate rows, walk-ins) turn out to be a grain mistake?

A grain is the answer to "what does one row stand for". One action, one payment, one visit, one member-month of attribution. It is a sentence written down next to the table, and everything else (a count, a rate, a join) is only correct relative to it.

Why every trap is a grain mistake: duplicate action rows break "one row per action" (the fix is COUNT(DISTINCT action_id)); a late payment run breaks "one row per action-month" (payments live at paid-month grain, so April is low and May is high, and the definition says so); double attribution breaks "one member per practice-month" (so attributed members count once per practice); walk-ins break "a visit belongs to the member's practice" (so the join key needs practice, not member alone). None of them is a bug in SQL. Each is a question asked at one grain and answered from a table at another.

Governance: who may change a metric's definition, and what happens to every report that cited the old version?

Here: a commit. Each metric in metrics.yaml has an owner (Head of Quality, Finance, VP Analytics, Head of Network) and the file has a version. Changing a definition is a pull request the owner reviews, and the version bumps (2026-10-07.1 to .2 when q14 was fixed, .2 to 2026-10-08.1 when visits arrived). request_capability can only return granted: false; the grant is the commit.

The old reports: every answer carried its version in cite_as, so a report that cited v.1 is identifiable, and the trace holds the SQL that produced it. What this build does not do: re-issue them. A production layer needs a rule for that (re-run, annotate, or let them stand with their version visible); the playground only makes the question answerable.

Cost: when does a semantic layer stop paying for itself, and is a seven-metric YAML file past that point or not yet near it?

It pays when the same number is asked by more than one asker, or by one asker more than once, or by anyone who did not write the SQL. Below that, a saved query is cheaper. The price is the discipline: an owner per metric, a version, a change process, and the refusals that follow ("no metric nobody defined").

Seven metrics is not yet near the ceiling; it is at the floor, where the layer is still cheaper than the alternative because the alternative is an agent writing SQL against five tables with five traps. The point it stops paying is organisational, not numeric: when nobody owns the definitions and the file rots, or when every question is a one-off an analyst answers once. The dated prices in prices.yaml are the same idea for the cost side: a drift watch, not a number.

Boundary: when is "ask by name" the wrong tool, and an analyst with raw SQL the right one?

When the question is new. Exploration, a hypothesis nobody has a metric for, a one-off investigation, reconciling two sources: that is analyst work with raw SQL, and the layer should get out of the way. "Ask by name" is for questions that recur and reach people who did not write the SQL: business users, dashboards, agents.

The build draws the line with a role, not a rule: analyst and admin may see member grain and every metric; nothing here gives any role a SQL tool, by design (ADR 0001), because the demo's point is the agent. In a real deployment the analyst keeps a SQL seat beside the layer, and the layer gains a metric the day an exploration turns into a question somebody asks twice. request_capability is where that handoff is logged.

Measured by what: how would you know the layer is working beyond "the evals pass"? What would lineage or a cost report have to show?

Four readings, all from the trace. Refusals over time by rule: a layer that is working refuses less as definitions and grants catch up with real questions, and the refusals it still issues are policy, not schema. Estimate against actual per answer: the two should agree, and the delta the guidance produced (487:1 here) should hold on real questions. Coverage: the share of metric-grain pairs the evals exercise; the payer grain had none and was broken for a day without a red light. Cost per answer by role and metric from cost_report, with the model side moving from estimated to exact once the SDK path exists.

What lineage adds: for any number on any report, the chain back to a trace id, a version, an owner and the SQL that ran. The build has the chain; a production layer has to keep it queryable (Tier 1 moves the trace into a table for that reason).

Unlocks: once every answer carries a trace id, what becomes possible that a dashboard never allowed: chargeback, replay, audit by question?

Chargeback: cost_report already sums warehouse and model cost by role and by metric; a principal is on every line, so a team can be billed for the questions it asked, not for a share of a dashboard nobody opens.

Replay: the trace holds the SQL and the arguments, so any answer can be re-run against today's data, or against the version that produced it, and the difference explained. Audit by question: "who asked for member-level data this month, and what did they get" is a filter on the trace, not an investigation. And the one the build points at: the question-and-answer pairs become the eval set. Real use grows the test suite, which is the closed loop the film ends on.

05The Kimball star

A fact table holds events with numbers on them, one row per event, at one declared grain. A dimension table holds the things the events are about, one row per thing. Facts in the middle, dimensions around them: a star.

Facts in the middle. Every dimension one join away.

A roll-up is a join to a dimension and a group by one of its columns. payer grain: join dim_practice, group by payer. month grain: join dim_date. member grain: join dim_member, the moment PHI is reachable.
