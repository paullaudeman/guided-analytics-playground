# ADR 0006 · Nothing is allowed unless a policy statement allows it

**Status:** accepted, 2026-10-07. Raised by Paul: *"explicitly permissions deny unless explicitly granted (AWS model)."*

**Context.** The first server enforced access as a set of separate `if` statements: grains carried a role list, `audit_log` hardcoded `ROLE != "admin"`, `cost_report` had no check at all, and no metric carried a role list, so an external practice could ask for payment figures because nothing said it could not. The practice scope was read only for the external role, so an admin entry with no scope saw everything by omission. Each gap had the same shape: a control that exists only where someone remembered to write an `if`, and silence that behaves as a grant. An adversarial audit the same day found the scope hole, the open `cost_report`, and a PHI list that was documentation rather than a control.

**Decision.** Access is a policy block in `metrics.yaml`, in the IAM shape: `default: deny`, one statement per role naming the tools, metrics and grains it may use (`"*"` is a deliberate grant of everything), and an explicit deny for PHI columns that wins over any allow. One function, `_authorize(tool, metric, grain)`, runs first in every tool and returns the rule that denied, naming the missing statement. A role with no statement gets nothing. A statement naming a tool that does not exist fails at startup. Scope (which rows) stays a separate axis: `PRACTICE_ID` is an existing practice number or the literal `all`; anything else refuses for every role. PHI is enforced at load: a metric whose SQL names a PHI column does not load.

**Consequences.** Adding a tool, a metric or a role grants nothing until a statement is written, which is the point. Every refusal is traced with the statement that produced it, so the audit log reads like `AccessDenied` with the policy name. `list_metrics` shows each role what it was granted. The smoke test asserts a role with no statement is refused everything, and asserts each of the audit's findings refuses with its own rule. What this does not do: read groups from an identity provider; that is Tier 2, and the policy keys on role names until then.
